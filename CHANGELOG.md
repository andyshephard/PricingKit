# Changelog

All notable user-visible changes to PricingKit are recorded here.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
PricingKit has no tagged releases yet; everything below is on its way to `main`.

## [Unreleased]

### Upgrade notes for self-hosters

1. **Make sure `ENCRYPTION_KEY` is set anywhere other than `npm run dev`.** Production builds (`npm start`, Cloudflare Workers) already needed it to sign anyone in, so a working production deployment is unaffected. What changes: login now checks for the key before contacting Apple or Google and explains how to set it (instead of a generic 500), and session cookies are no longer read as plaintext base64 anywhere except `next dev`, including when `NODE_ENV` is unset or non-standard. If you ran without `NODE_ENV=production` and without a key, existing sessions stop working and sign-in is refused until you set one. Generate a key with `openssl rand -base64 32` and set it in `.env.local`, your process environment, or as a Worker secret (`npx --no-install wrangler secret put ENCRYPTION_KEY`). Earlier README text called the key "recommended"; that was wrong.
2. **Node 22 or later** is now declared in `package.json` `engines`; `.nvmrc` pins the version CI uses (22.23.3).
3. **Scripts calling `?refresh=true`** on `/api/ppp` or `/api/exchange-rates` must now send a valid Google or Apple session cookie, or they get `401`. Plain reads without `refresh` are still public. A refresh re-fetches exchange rates only with the user's own key (from Settings), never the operator's, and World Bank PPP at most every 10 minutes.
4. **Clients of `/api/bulk`** must preview first: send `dryRun: true`, then the same request with `expectedPrices` built from the preview (`{ "<id>" or "<id>/<basePlanId>": { "<region>": "<oldPrice>" } }`); a write without it is refused (`400`). A `fixed` operation needs `currency`. `oldPrice` / `newPrice` are now exact (`"USD 9.99"`, no rounding to two decimals). Read the per-result `success`, `error` and `skippedRegions` fields. The top-level `success` is now `false` when nothing was written. A subscription item sent without a `basePlanId` now produces one result per base plan (each carrying its `basePlanId`), so `total` and `results` count base plans for subscriptions, not request items.
5. **Optional `TRUSTED_CLIENT_IP_HEADER`.** Set it to `cf-connecting-ip` on Cloudflare (or the header your own proxy sets) to rate-limit anonymous Open Exchange Rates key tests per client. Without it they share one per-instance limit.
6. **Forks importing the pricing maths** should change `@/lib/google-play/currency` to `@/lib/pricing` and `@/lib/conversion-indexes/*` to `@/lib/pricing/indexes/*`. The functions are unchanged.
7. **`ENCRYPTION_KEY` must be base64 of at least 32 bytes with at least 16 distinct byte values** (what `openssl rand -base64 32` prints; a random 64-character hex key also qualifies). This checks the format and refuses obvious repeats; it can't check randomness, so generate the key. Outside `npm run dev`, any other value (a passphrase, a short string) now refuses every session: sign-in fails with a message saying so, and everyone is signed out. If yours doesn't qualify, set a new one; everyone signs in again once. The key's decoded bytes now feed the key derivation, which is why a conforming key's old cookies are migrated (below) but a replaced key's aren't.
8. **Sessions expire on the server, and cookies are renamed.** Session cookies now hold an encrypted envelope with an absolute 24-hour expiry, and in production every cookie is named with the `__Host-` prefix (`__Host-gplay_session`, `__Host-apple_session`, `__Host-gplay_package_name`, `__Host-apple_bundle_id`, `__Host-exchange_rates_api_key`). Cookies of the earlier formats and names are still read until **2026-11-10 00:00 UTC** and re-written in the new format and name on the request that reads them, so with a conforming key nobody is signed out by the upgrade; from that date they are refused. Rolling back to an older build would not read the new cookies (users sign in again). Set `SESSION_VERSION` (any value; change it later) to sign everyone out at once; while it is set, old-format cookies are refused.
9. **Plan hashes are longer.** Every plan is confirmed with a 32-digit SHA-256 hash, whatever its schema version; a plan written by an earlier build is still read, but its old 16-digit hash no longer confirms it: run `pricingkit diff` on it for the new one. A script that checks the hash's length should expect 32.
10. **Run logs from earlier v2 builds can't be resumed or undone.** A run log records its plan's hash, and run logs are now read only with the 32-digit SHA-256 hash. A log written before that change (16-digit hash) is refused by `pricingkit apply --resume`, `--resume-runs`, `pricingkit undo` and the MCP `apply_command` tool. Finish or undo such a run with the build that wrote it before upgrading; its plan can still be applied afresh (run `pricingkit diff` for its new hash).
11. **`NEXT_PUBLIC_SITE_URL` now defaults to `https://pricing-kit.com`** (it was `http://localhost:3000`). It sets canonical and social-preview URLs, `sitemap.xml` and `robots.txt`, and is read at build time. If you host PricingKit on your own domain, set it in the build environment; for local absolute URLs set it to `http://localhost:3000` in `.env.local`.
12. Nothing else needs configuring. There is no database and no session file.

### Added

- **Atlas redesign.** A new look for the whole site, light and dark: the theme follows the system until you pick one with the toggle (remembered in this browser), applied before the first paint; Manrope and IBM Plex Mono, self-hosted. A new landing page; an app shell with a grouped sidebar and app switcher; restyled connect, list, subscription, settings, index checker and setup guide screens; and a top bar on every app screen, Settings included, with the breadcrumb, search, refresh and Sign out (it still clears both store sessions, the saved Open Exchange Rates key and the tab's flag, and reports a sign-out the server didn't confirm). Every bulk price change now ends in the same review step: decreases, increases and new prices, each country before and after with the percentage, the note about existing subscribers, Download plan, then Apply. That includes the Google Play bulk update (its preview and the previewed-price check are unchanged; repeated selections are listed) and creating or re-pricing an App Store promotional offer from a rule (Download plan gives the plan JSON; Apply stays disabled without a plan hash). The Offers cards on subscription pages are restyled; Google Play offers stay read-only. Colours come from theme tokens, so status colours (lower and higher prices, warnings, errors) are readable in dark mode.
- **Docs at `/docs`.** The README's content, SECURITY.md and this changelog, rewritten as 19 pages: getting started (connecting each store, running it yourself), pricing (strategies, plans, existing subscribers, proceeds, reference data), offers, the command line (install and credentials, commands, spec and rules files, workspaces, agents) and reference (security model, changelog). A sidebar (behind a menu button on phones), an "On this page" list, copy buttons on code blocks, and a search over page titles and headings that runs in the browser. Built with the site, so every deployment has its own copy. The README is now a short overview that links to them. The footer's Changelog and Security links and the connect screen's "How keys are handled" open these pages instead of GitHub.
- **`sitemap.xml` and `robots.txt`** list the landing page, setup guides, index checker and docs, and keep crawlers out of the app and the API.
- **Workspaces: several apps on both stores.** A `pricingkit.workspace` file lists App Store bundles and Google Play packages, each with its spec, rules and offer plan spec (by path or inline). `plan --workspace` writes one plan per app (and per offer plan spec) plus a `workspace-plan.json` index with one hash; `diff`, `apply` and `undo` take `--workspace-plan`. Plans never mix apps: each is applied through an adapter for its own app, with its own run log, after every plan's hash and app and every app's pin are checked.
- **Cross-store parity.** Workspace parity mappings tie an App Store subscription to a Google Play base plan. A mapping's `target` drives both stores (each snaps it separately), and the plan reports per territory where the two still differ; `pricingkit parity --workspace` reports the current gaps, read-only (exit 2 above the mapping's threshold, exit 1 when a territory couldn't be compared or nothing is priced on both stores).
- **Prices CSV.** `pricingkit export --format csv [--offers]` (and `--workspace`) writes base and offer prices per territory as a `pricingkit.prices` v1 CSV with a version line; the web app's export menu offers the same file. A spec or offer plan spec imports it as fixed prices with `pricesFile`, checked against real price points; the plan lists rows that don't snap exactly. Each row names its product type (`product_type`), so App Store in-app purchase rows are recognisable (and refused on import). Round trip safe; errors name the line and column, never a cell.
- **Per-product base territory.** A spec product may give `baseTerritory`, which a strategy target without `base.territory` uses; there is no app-wide default. In the web app, an App Store subscription remembers its own base territory for bulk pricing and the subscription list, and in-app purchase bulk pricing starts from the product's own schedule base territory instead of the app's.
- **Proceeds targets.** A spec product with `"measure": "proceeds"` targets what you receive (net of tax and the store's commission) instead of the customer price: App Store prices snap to the price point with the nearest proceeds; Google Play prices `target / (1 - commission)` as the tax-exclusive price (`"commission"`, default 15%). Plans record proceeds and Play's tax per op, and `pricingkit diff` shows Proceeds and Tax columns.
- **What existing subscribers see.** Every base-price change in a plan is classified per territory (lower price, new subscribers only, notified without consent, needs consent) from App Store Connect's consent rules and per-storefront thresholds and Play's legacy-cohort and opt-out rules; `pricingkit diff` shows it, with the assumptions it made. `"consent": { "maxIncreaseWithoutConsent": true }` refuses a plan in which any territory would need consent (`CONSENT_REQUIRED`); `billingPeriod` and `lastIncreaseAt` sharpen the check. The Apple subscription preview in the web app shows the same, plus current proceeds.
- **Custom multipliers.** The `custom` strategy works: a per-territory multiplier table in the spec, or a CSV (`multipliersFile`, e.g. a price export with a `multiplier` column), validated. The web app's bulk pricing modals offer Custom again, with a table input; territories without a multiplier are not priced.
- **Reference data freshness.** Plans record the data their targets came from and its age, and warn when it is older than a limit (`freshness.maxAgeDays`; `freshness.refuseStale` refuses). Stale PPP data is skipped (default: older than 3 years) or inflated by CPI ratios (`pppStaleness`). `/api/ppp` reports each country's PPP data year, applies the same policy (`?pppStale=cap|inflate&pppMaxAge=`, CPI from the World Bank), and returns freshness metadata and the exchange-rate timestamp; the index checker and bulk pricing modals show freshness badges.
- **`scripts/fetch-apple-price-tiers.ts`** regenerates the static Apple price tier table from the live API (read-only, needs credentials, `--dry-run`).

- **`pricingkit apply --allow-base-prices`** applies plans that change base prices (a base-price spec, a combined `plan --spec --rules` plan, or the undo plan of such a run), App Store and Google Play. Same safety as offer plans: `--confirm` with the plan hash before anything is read, the run log saved before and after every write, `--resume`, `undo`, the subscription checked against the plan's app, the `PRICINGKIT_EXPECT_*` pins, and in a combined plan offers applied only after the base prices they were derived from. Without the flag such a plan is refused before any store request. The printed resume command keeps the flags it needs. **App Store caveat:** two App Store Connect behaviours this relies on (an immediate price change replacing the territory's older entries; a second scheduled price created before the old one is deleted) are not yet confirmed on a test app; `plan` and `apply` say so. Try a small plan on a test app before relying on it.
- **`pricingkit offer deactivate|activate|delete`** plans one lifecycle change of an existing App Store or Google Play offer and writes it as a plan file; apply it with `pricingkit apply --confirm` (and `--force-delete` for deletes). Deactivating an App Store introductory or win-back offer sets its end date (`--end-date`). What the store doesn't allow (deactivating a promotional offer, deleting an offer code or an active Play offer) is refused with the reason and no plan is written.
- **Strategy targets in pricing specs.** `{ "type": "strategy", "strategy": "ppp" | "bigmac" | "netflix" | "direct", "base": { "territory", "amount" }, "rounding" }` spreads one base price to every territory with the same price-parity maths as the web app's bulk pricing, then snaps to real store prices as usual. Built-in indexes and fallback exchange rates keep plans reproducible; `exchangeRates` in the spec overrides rates.
- **YAML spec and rules files.** `plan --spec` and `plan --rules` accept `.yaml` / `.yml` files. Numbers keep the digits written (`4.10`, IDs with leading zeros); tags, several documents per file and duplicate keys are refused, and errors give line and column only. Adds the `yaml` package (no dependencies of its own), used by the CLI only.
- **`pricingkit export --in-app <product id>`** exports an App Store in-app purchase (manual and automatic prices, scheduled prices and the price schedule's base territory, read strictly from App Store Connect's relationships) or a Google Play one-time product as a `pricingkit.state` snapshot. State snapshots may now carry `baseTerritory` (optional).
- **`pricingkit mcp`**, an MCP server over stdio for agents: `offers`, `plan` and `diff` tools, and `apply_command`, which returns the start of the `pricingkit apply` command for a person to finish (see Security). There is no apply tool: agents plan, people apply. Arguments are typed and can't start with `-`; file paths use a safe character set, no `..` or `.git/`, and must resolve inside the server's working directory (symlinks included); `plan` never replaces a file that isn't a plan or state file; the returned command is shell-quoted and a resume log must belong to the plan.
- **Google Play subscription offers.** `pricingkit offers --package-name` lists a subscription's Play offers (one base plan with `--base-plan`, or all of them) with their state, eligibility, tags and each phase's price per region; the Google subscription page shows the same list (read-only). An offer plan spec for a Play app (`play.offer` offers) plans creating, changing and activating offers: relative discount (Play's own "X% off", which follows the base price), absolute discount, fixed prices, percent of each region's base price (made a valid price by Play's price conversion) or a free trial; eligibility "never had any subscription" / "never had this subscription", upgrades, or developer-determined; offer tags such as `rc-customer-center`. The preview shows each offer's eligibility, phases and tags and, per region, the base price, offer price and discount. `pricingkit apply` applies Play offer plans with the same safety as App Store ones: the plan hash as confirmation, idempotent and resumable (a create that took effect is never sent twice; one whose activation failed resumes with the activation only), undo (an activated offer is deactivated, since Play deletes only drafts), every request within the budget, and a plan for another package refused with `APP_MISMATCH` before anything is read. Deleting a draft offer needs `--force-delete`. Offers Play returns in a shape PricingKit can't read exactly are shown with their problems and never written to.
- **Offer rules files cover Google Play.** A rules file for a Play app (`packageName`) lists Play offers with `percentOfCurrent`, `fixed`, `play.relativeDiscount` or `play.absoluteDiscount` rules. `pricingkit plan --rules` re-prices percent-of-current and fixed-price offers after base price changes (also together with a base-price spec, offers after the base prices they depend on); relative-discount offers are listed as "follows base automatically".
- **Play offer plans show and guard what changes besides prices.** The plan preview and `pricingkit diff` show each offer's state, eligibility and tags before and after (also in the `pricingkit.planSummary` JSON), with named warnings such as "removes tag rc-ignore-offer". A spec that leaves out a tag the offer has is refused unless it sets `play.allowTagRemoval`. A percent-of-current region whose Play price is further from the target than `play.deviationThreshold` (default 5%) is left out and `pricingkit plan` exits 1. Fixed prices and amounts off must fit the currency's decimals. Relative discounts other than 50% get a warning until their meaning (the share taken off) is confirmed on a test app.
- **Play offer creates and activations are never resent after a 5xx or a timeout.** They are retried on 429 only; a failed create counts as "may have applied", and the next read or a resume decides. Undo deletes the draft a failed create may have left and lists an activation that got no answer as not reversible, instead of deactivating an offer that may not be active.
- **`PRICINGKIT_EXPECT_BUNDLE_ID` / `PRICINGKIT_EXPECT_PACKAGE`** pin the CLI to one app: any other is refused (`APP_NOT_EXPECTED`) before anything is read.
- Known gaps, to be checked on a Play test app: the 409 answer to a duplicate offer ID, which state changes Play allows, how a developer-determined offer reads back, the regions version taken from Play's price conversion, patching an active offer's eligibility or tags, and Play's rounding of discounted prices (previews show estimates).

- **Offers stay in step with base prices (sync).** An offer rules file (`pricingkit.offerRules`, checked into your repository) lists existing App Store offers and the "X% of each territory's price" rule each follows. `pricingkit plan --rules <file>` re-prices every offer marked `syncWithBase` that no longer matches today's base prices. `pricingkit plan --spec <base spec> --rules <file>` plans base prices and the offers re-derived against the new prices (not the current ones) in one plan; applying it changes the base prices first, and an offer is re-priced only once the base prices it was derived from are in place (otherwise it fails with `BASE_NOT_APPLIED` and nothing is sent). Only promotional offers can be re-priced: offer codes, win-back and introductory offers that need new prices are listed as manual actions with what to do, and PricingKit never deletes or re-creates an offer by itself. Territories whose base price is scheduled for a later date are held by default (offer prices would change immediately, before the base), while the offer's other territories are re-priced; `--scheduled-base now` re-prices those offers anyway, with a warning. `pricingkit diff` groups base prices and offers and lists manual actions. `pricingkit apply` still applies offer plans only, so it applies `plan --rules` plans but refuses a plan that also changes base prices; change base prices in the web app, then run `plan --rules`. Google Play offers aren't covered yet.
- **Subscriptions are checked against the app before any write.** App Store Connect API keys work across a team's apps, so a subscription ID from another app (for example production, copied into a staging plan) would have been written to. Offer plans, the executor, the offer routes and the subscription price edit, delete and clear-scheduled routes now refuse a subscription outside the signed-in or planned app with `APP_MISMATCH` (409). This costs three extra reads per run. A subscription price delete must also name a price of that subscription. In-app purchase and app price edits were already limited to the signed-in app.
- **Create and update Apple subscription offers from a rule.** On an Apple subscription page, "Create offer from rule" creates a promotional offer priced at a percent of each territory's own current price (basis, snapping, duration, mode, offer code and name), and "Update prices to rule" re-prices an existing promotional offer to such a rule. Both preview every territory first, apply only after a confirm dialog showing the counts, and end with the run result and its log to download. The web flow does promotional offer creates and re-prices only; the log isn't saved and there is no resume or undo from the web (use the CLI).
- **Offer plans** (library and CLI): plans (`pricingkit.changeset`) can now create promotional offers, introductory offers (per territory, with overlap detection), offer codes and win-back offers, replace a promotional offer's prices, end or reactivate offers, and delete them. An offer plan spec (`pricingkit.offerPlanSpec`) plans several products in one go, each with its own offer key. Applying is idempotent and resumable: offers are found by their key, so a create that timed out but took effect is never sent twice. A plan that changes offers applies only with its hash as confirmation, and deleting an offer needs an explicit force option because App Store Connect doesn't report redemptions. Things Apple refuses (an 11th promotional offer, editing an existing offer's duration, re-pricing an offer code) are refused at planning with the reason. Undo plans list what can't be undone, such as redeemed offer codes.
- **`pricingkit undo <plan.json> <run.json>`** writes the plan that undoes a run, offline, and lists what can't be reversed; apply it with `pricingkit apply --confirm`. The web offer dialog now offers the plan as well as the run log for download and shows the CLI commands to resume or undo a web run.
- **`pricingkit apply <plan.json> --confirm <hash>`** applies an App Store offer plan and saves the run log after every step; `--resume` continues a run. `pricingkit plan` accepts an offer plan spec, and `pricingkit diff` summarises offer ops.
- Known gaps, to be checked against a test app: what the duration means for pay-as-you-go offers, the 10-promotional-offer limit, and free-trial and win-back price details on create. Confirmed on a real account: free-trial offer prices have no price point, and a pay-up-front promotional offer's price is the total for its whole duration. Confirmed on a test app with PricingKit's own writes: inline price IDs work for promotional offer creates; a promotional offer price update replaces the whole price list (175 prices afterwards, no duplicates); a create that answered a transient 500 having created nothing was found missing on resume and created once; and the confirm gate, idempotent re-apply, undo of a re-price and undo of a create (refused without `--force-delete`, deleted with it) worked as described.
- **`pricingkit` command line (read-only).** Run it from a clone (`node /path/to/pricingkit/bin/pricingkit.mjs`; see the docs, Command line). Commands: `export` (current prices of an App Store subscription or Google Play base plan as a `pricingkit.state` snapshot), `plan --spec <file>` (a dry run that turns a pricing spec into a plan file and never writes to a store), `diff` (a readable summary of a plan), and `offers` (an App Store subscription's offers with prices per territory). Every command takes `--json` for machine-readable output and `--budget` to cap store requests. Exit codes: 0 OK, 1 error, 2 a plan with changes, so CI can gate on them. `--budget` defaults to 1000 requests. Credentials come only from environment variables (`ASC_KEY_ID`, `ASC_ISSUER_ID`, and `ASC_PRIVATE_KEY`, `ASC_PRIVATE_KEY_HEX` or `ASC_PRIVATE_KEY_PATH`; `GOOGLE_APPLICATION_CREDENTIALS` or `GOOGLE_SERVICE_ACCOUNT_JSON`); the docs (Install and credentials) have a macOS Keychain recipe. A key that can't be imported is refused up front, naming the variable. Credentials are never printed, written to disk or logged, and all output is scrubbed of key material and minted tokens as a backstop. `plan` never replaces its default output file (`pricingkit-plan.json`) without `--force`. There is no `apply` command yet. Adds `tsx` as a dependency to run the TypeScript without a build step.
- **Pricing spec** (`pricingkit.spec`, version 1, JSON): base-price targets for `plan`, either fixed prices per territory or a percentage of each territory's current price, snapped to real store prices when planning. Library: `parsePricingSpec` and `specTargets` in `src/lib/pricing`.
- **Subscription offers on Apple subscription pages (read-only).** A new Offers section lists a subscription's introductory offers, promotional offers, offer codes and win-back offers with their terms, eligibility and price in every territory. Prices are read from App Store Connect's relationships only: a price without a territory, price point or currency is shown as a problem, never guessed. Nothing can be created or edited yet.
- **Offer prices from a rule.** "X% of each territory's current price" (per billing period, or in total over the offer's duration, e.g. a 1-year pay-up-front offer on a monthly plan = 12 x price x X%) with a snapping mode (the basis defaults to the whole duration for pay-up-front offers), snapped to each territory's own subscription price points. Library: `deriveOfferPrices` in `src/lib/pricing` (per-territory preview: current price, exact target, snapped price, price point, deviation, proceeds, with flags when the offer isn't below the current price, no price point fits, or snapping moves the price more than 5%).
- Known gap (since confirmed: free-trial offer prices have no price point): whether App Store Connect returns a price point for free-trial offer prices, and how pay-as-you-go offer durations relate to the billing period, are read from the API reference, not yet confirmed against a real account.
- **Plans you can review, apply, resume and undo** (library, `src/lib/pricing` and `src/lib/adapters`; no UI yet). A plan is a JSON file (`pricingkit.changeset`) listing every price change with the price expected before and the price set after. Applying it checks each territory first: one already at its target is skipped, one that changed since the plan was made is reported and left alone, so applying a plan twice changes nothing the second time. Each run keeps a JSON log (`pricingkit.applyRun`), saved before and after every write, that can be resumed after a partial failure or a crash and turned into an undo plan. If the log can't be saved, the run stops before writing anything else. Covers base prices of Apple subscriptions and Google Play base plans and one-time products. Current prices can be saved as JSON (`pricingkit.state`); Phase 0 price exports import as state.
- Known gap: how App Store Connect lists a subscription's prices right after an immediate price change, and whether it accepts a second scheduled price before the old one is deleted, are not yet verified against a real account. The executor re-checks state before writing and refuses ambiguous prices, but these paths should be tried on a test app before production use.
- **Snapping to real store prices.** The Apple adapter snaps each territory's target to that territory's live subscription price points. The Google Play adapter snaps through Play's own `convertRegionPrices`, allowing for each region's tax.
- The pricing maths is now a framework-free core with exact decimal money; a test keeps Next.js, React and network code out of it.

- **Price export.** Product and subscription detail pages (Google and Apple) have an "Export prices" menu that downloads the current prices as CSV or JSON. Google subscriptions export per base plan; Apple subscriptions include scheduled prices. Backed by the read-only `GET /api/export` endpoint, which never writes to a store. The JSON format is versioned (`schemaVersion: 1`). An Apple in-app purchase export fails, rather than guessing, if its base territory can't be read.
- **Retries with backoff** for Google Play and App Store Connect calls. 429, 5xx and network errors are retried up to 4 attempts with jittered exponential backoff, honouring `Retry-After` up to 60 seconds. App Store Connect creates (POST) are retried only on 429: after a 5xx, timeout or network error the create may already exist, so it is reported instead of being sent again. Apple's hourly `X-Rate-Limit` is tracked: a 429 is not retried when it reports 0 requests remaining; callers that pass a `RequestBudget` stop sending entirely.
- **CI.** GitHub Actions runs tests, `npm run typecheck` and lint on every pull request and push to `main` and `v2`. Dependabot opens weekly grouped dependency updates.
- `npm run typecheck` script.
- `SECURITY.md` with private vulnerability reporting and the credential-handling model.

### Changed

- `PRICINGKIT_EXPECT_BUNDLE_ID` and `PRICINGKIT_EXPECT_PACKAGE` accept a comma-separated list of apps.
- Strategy plans now warn when the built-in data they use is stale; the fallback exchange rates (2026-02-01) already are by the default 45-day limit. Give `exchangeRates` with `exchangeRatesAsOf` in the spec, or raise `freshness.maxAgeDays`. From 2028, PPP strategy plans skip territories unless the PPP snapshot is refreshed, `pppStaleness.maxAgeYears` is raised, or the inflate policy is used.
- **Plan files are schema version 3.** Version 2 added two planner-note fields, `priceChanges` and `dataFreshness`, which are not covered by the plan hash; version 3 marks plans confirmed with the SHA-256 hash (see Security). PricingKit reads versions 1 to 3. A plan from a newer version is refused with "written by a newer PricingKit; upgrade". Older builds refuse v3 plans.
- `pricingkit diff` labels proceeds, tax, existing-subscriber, consent and reference-data output as planner notes not covered by the plan hash. It recomputes each immediate change's existing-subscriber class from the op, and prints a WARNING when the stored note disagrees.
- Spec dates must be real days (2026-02-30 is refused). A `consent.lastIncreaseAt` that can't be used, or that falls after the change takes effect, counts as needing consent instead of being ignored.
- The Apple "Preserve existing subscriber prices" copy now says it applies to increases; decreases always reach existing subscribers.

- **Undo plans now revert base-price ops that failed after being sent**, since an App Store create that answered 5xx may have taken effect; if it didn't, applying the revert skips it as already at target. The executor now checks a `confirm` hash whenever one is passed, not only for offer plans.
- **`pricingkit apply` no longer refuses every plan with base prices**: it asks for `--allow-base-prices` instead (see Added). Earlier entries below that say `apply` applies offer plans only describe the behaviour before this change.

- **Google Play base plan price edits send Play's current regions version** (from its price conversion) instead of the fixed "2025/03", or the version a CLI plan recorded (`options.regionsVersion` on each op). Play's subscription resource has no regions version of its own. If Play reports none, the edit is refused. This costs one read-only request per edit (per run for the adapter).

- **Library: offer ops of either store.** `ChangeOp` can now hold a `PlayOfferOp` (`platform: "google"`, offer kind `play.offer`); `OfferOp` is still the App Store op and `AnyOfferOp` is either. `isOfferOp` is true for both; use `isPlayOfferOp` / `isAppleOfferOp` to tell them apart. Adapters may implement `verifyApp(app)`, which the executor calls before reading anything (both built-in adapters do).
- **Library: Play offer eligibility is typed.** The reserved `{ type: "play.targeting", rule }` eligibility now takes a typed rule (`developerDetermined`, `acquisition` or `upgrade`) instead of any object.

- **Library: the executor applies ops in dependency order.** An op runs only after the ops it `dependsOn`, and otherwise base-price ops go before offer ops; previously a plan's ops ran in product order with offer ops possibly in flight alongside base-price ops. Offer ops may depend on base-price ops of their product (sync plans) and base-price ops on offer ops (their undo plans: offers revert first, and a base price isn't reverted if its offer's revert failed, `OFFER_NOT_APPLIED`). Plans may also carry `manualActions` (planner notes). Files without these fields are unchanged.
- **Library: a ChangeSet's `ops` can hold offer ops.** Code that reads `changeSet.ops` as base-price ops should use `basePriceOps(changeSet)`. `parseChangeSet` accepts the offer op kinds instead of refusing them as reserved; `setAvailability` and `migrateCohort` stay reserved.
- **Bulk Apple routes and `/api/bulk` run within a request budget.** Each run gets its own budget (3,600 requests by default, Apple's hourly allowance per key) that also tracks Apple's `X-Rate-Limit`. Every request a run sends, including reads and pagination, is counted, and the run stops before sending once either limit is reached. The Apple price-point resolver now stops with an error when the budget is spent instead of marking every remaining territory as skipped.
- **Fewer and gentler Apple reads.** The Apple products list reads base prices 4 at a time instead of all at once, and subscription price points are read 8,000 per request (one request per territory instead of about four). Apple in-app purchase price updates by price point are sent one territory at a time.
- **Apple in-app purchase list no longer assumes USA.** A product whose price schedule names no base territory is listed without a price and flagged (`priceUnavailableReason: "BASE_TERRITORY_UNKNOWN"`) instead of showing its US price.
- When Apple refuses a subscription price with 409 and the territory already has a scheduled price, the error now names that scheduled price for immediate changes too. Nothing is deleted on a 409.
- **Testing an Open Exchange Rates key without signing in is rate limited** (429 with `Retry-After`): 50 tests per instance per 10 minutes, and 5 per client when the new optional `TRUSTED_CLIENT_IP_HEADER` names the header your proxy sets to the client IP (e.g. `cf-connecting-ip` on Cloudflare). Client IP headers are ignored unless configured, because clients can forge them. Signed-in users are not limited.

- **Google Play region edits no longer launch or re-enable regions.** Editing prices on a subscription base plan or one-time product changes only the regions you edited. Previously every save turned on new-subscriber availability for all regions, auto-filled every unconfigured region with a price converted from the US price, and required a US price. Other regions, availability settings and other base plans are now sent back exactly as Google returned them, and the product keeps its own `regionsVersion`. If Google needs something more (for example a USD/EUR price), you see Google's error instead of PricingKit guessing prices.
- **Untouched one-time product regions are kept as they are.** Regions with no price are no longer rewritten to a USD 0 price on save.
- **Sign-in and app switching are read-only.** Connecting a Google account or switching apps no longer sends a no-op PATCH to test write permission. If your service account lacks pricing permission, you find out on your first price edit (403).
- **`ENCRYPTION_KEY` is checked up front.** Production builds already required it to create a session; login now checks for it before contacting Apple or Google and shows a message explaining how to set it. The requirement now applies whenever `NODE_ENV` is not `development` (previously only when it was `production`), so an unset or non-standard `NODE_ENV` no longer allows plaintext sessions (see upgrade notes).
- **Missing exchange rates are an error, not USD parity.** A region whose currency has no exchange rate used to be priced as if 1 unit = 1 USD. It is now shown as "No exchange rate", cannot be selected in the bulk pricing modals and is never applied. If the base region has no rate, an Apple update is blocked. The Index Checker shows these regions as flagged instead of a price.
- **"Custom" pricing strategy is hidden** in the bulk pricing modals until per-territory multipliers exist. PPP, Big Mac and Netflix are unchanged.
- **Rounding rounds down.** The bulk "round" operation now rounds to the nearest price ending at or below the current price (12.00 becomes 11.99, not 12.99). Zero-decimal currencies such as JPY and KRW get whole-number prices. Subscription base plans use the same rounding as products.
- Live World Bank PPP multipliers are clamped to 0.1–2.0, like the static indexes.
- **Bulk updates report what they skipped.** `/api/bulk` now marks items where none of the target regions had a price as failed and lists skipped regions with a reason. The bulk modal shows them and no longer says "Successfully updated 0 items".
- **Bulk subscription items without a base plan apply to every base plan.** A subscription item sent to `/api/bulk` without a `basePlanId` is applied to each of the subscription's base plans, with one result per base plan, so a failure in one base plan does not hide the others. `stopOnFailure` still stops the rest, and the base plans not attempted are reported as skipped. A subscription with no base plans, or a `basePlanId` that matches none, is a failed item. The bulk modal labels subscription results by base plan.
- The generic bulk update button was removed from the Apple products and subscriptions list pages. It called the Google-only `/api/bulk` endpoint and could not work for Apple. Use the Apple bulk pricing modals instead.
- **Apple subscription price edits keep scheduled prices.** New prices are created before the scheduled price they replace is deleted. If the create fails, nothing is deleted. When a territory already has a scheduled price and Apple answers 409, the error names that scheduled price and asks you to clear it first and apply again (Apple uses 409 for ordinary validation errors too, so PricingKit never deletes on a 409). The result lists each territory's outcome and is not reported as a success if any territory failed.
- `?refresh=true` on the public `/api/ppp` and `/api/exchange-rates` endpoints requires a signed-in session (see upgrade notes).
- Settings no longer returns any part of an operator's `OPEN_EXCHANGE_RATES_APP_ID`. A key you saved yourself shows only its last 4 characters.
- The site and README now describe credential handling accurately: credentials are sent to the PricingKit server you use, encrypted into an HttpOnly cookie, and not stored server-side.

### Removed

- The unused `next-themes` dependency (the theme toggle never used it).
- **Offer drift checks.** The `pricingkit drift` command (one offer, `--rules` and `--workspace`), the `pricingkit.offerDrift`, `pricingkit.playOfferDrift`, `pricingkit.rulesDrift` and `pricingkit.workspaceDrift` reports and their exit codes, `GET /api/apple/subscriptions/{id}/offers/drift`, the web app's "Check against rule" view, the MCP `drift` tool and the library's `checkOfferDrift`, `checkRulesDrift`, `checkPlayRulesDrift` and adapter `checkOfferDrift` / `checkRulesDrift` are gone. Rules files stay: `pricingkit plan --rules` still re-prices `syncWithBase` offers after base price changes (and a plan with no ops means every synced offer is in step), and "Update prices to rule" in the web app plans a re-price from the rule you enter. `syncWithBase: false` rules are now simply ignored.
- **The example GitHub Actions workflows** (`examples/github-actions/`: a weekly drift check, plan on pull request, apply on merge) are gone. Workflows that hold store credentials need more care than a copied template gives them (who can read repository secrets, which runs a resume trusts), so PricingKit no longer ships them. The CLI's exit codes still let you build your own.

### Fixed

- `pricingkit apply` wrote its default run log (`<plan>.run.json`) to the current working directory instead of next to the plan file, so `apply plans/x.json` run from elsewhere left `x.run.json` in the wrong place (and a second apply from another directory didn't see it). It is now written next to the plan. `pricingkit undo`'s default `<plan>.undo.json` had the same problem and is fixed too. `--run-out` and `--out` still resolve against the working directory.
- A failed Google access-token request is now thrown as a `GooglePlayApiError` (a real `Error`, still `code: 401` with reason `invalidCredentials`, not retried) instead of a plain object, so anything that prints it shows Google's message instead of `[object Object]`.
- Plan, state and run files that aren't valid JSON are refused with "not valid JSON" only. The parser's message, which can quote the file's contents, is no longer passed on.

- **Editing several Apple in-app purchase territories by price point kept only the last one.** Apple's price schedule create replaces the whole schedule, and PricingKit sent one schedule per territory, each making that territory the base. It now reads the current manual prices and sends one schedule: the territories you changed, every other territory's manual prices as they were, and the product's existing base territory. An immediate change keeps the territory's scheduled prices (they still take effect; the response lists them as `keptScheduled`), and a future-dated change keeps its current price until then. A product without a schedule takes one immediate price, which becomes its base territory.
- **Calculated (PPP) prices for an Apple in-app purchase no longer reset the territories you didn't send.** Territories left out of the bulk update, or skipped because no price point matched, used to lose their manual price and fall back to Apple's automatic one; they now keep it. If the base territory's price can't be resolved, nothing is changed (422).
- The Apple products list and app price reader dropped the cursor from Apple's next-page link, so an app with more than one page of in-app purchases or prices re-read the first page instead of moving on. All Apple list reads now share one pagination helper that follows the next link exactly, and stop with an error rather than return a silently truncated list.

- The bulk update button on the Google subscriptions list page failed every selected subscription, because it sends no base plan. It now updates each subscription's base plans.
- Deleting a Google one-time product region price reported success without changing anything. It now removes the region. Deleting a base plan region removes exactly that region instead of re-filling the others.
- Google 400/409/412 rejections on subscription base-plan price edits and on region deletes now return Google's status and reason instead of 500.
- An Apple in-app purchase price update without a base territory price reported success without writing anything. It now fails with a 422 explaining the missing or unsupported base territory.
- Apple in-app purchase list and price read errors were shown as products without prices. They now show the real error; a product with no price yet still shows without one.
- Apple subscription read errors (auth, rate limit, server errors) were shown as "Subscription not found" or as an empty price list. They now show the real error, and a genuine 404 still shows "Subscription not found".
- The Apple subscription price-tier picker showed "No price tiers available" when loading failed. It now shows the error with a Retry button.
- A completed Apple subscription write is no longer reported as failed when only the follow-up refresh fails.
- Error messages no longer read "[object Object]", and Google-shaped errors such as `{ code: 429 }` are now treated as retryable by the shared rate-limit helper.
- Network failures while fetching a Google access token are now retried.

### Security

- **Hardening.** The MCP server also masks anything shaped like a confirm hash (32 or more hex digits) inside every JSON string value and key of a tool result, not only in the hash fields and stderr. Removing hashes from MCP output is a speed bump, not a gate: an agent that can run code can recompute a plan's hash; the typed confirmation of `pricingkit apply` at a terminal is the gate. `pricingkit apply` with stdin redirected but stderr a terminal (`< /dev/null`) now prints the summary and requires `--yes`, so skipping the question is visible. `/api/bulk` lists items and base plans it dropped as already covered (`duplicates`). The route-guard test now checks that `rejectCrossSite` is the `@/lib/request-guard` export and flags `.body` reads and destructured body readers on requests.
- **No more CSP reports from zod in the browser.** zod 4 probes once whether it may use `new Function`; the Content-Security-Policy refuses it (as it should), but the browser reported a violation on every page that loaded a schema, including the landing page through a prefetched link. The browser now runs zod without the probe (`src/instrumentation-client.ts`); parsing is unchanged.
- Smaller fixes: Google Play routes no longer return upstream error text in a `500` (it is logged instead); the CSV formula guard also covers a leading line feed and the full-width `＝ ＋ ＠ －`; an App Store adapter whose credentials name no app refuses every plan; Dependabot and CI also cover the `v2` branch. Deactivating an offer and removing a Play region's price keep needing no force flag, deliberately: both are reversible, and `diff` and the `apply` summary show them.
- **The MCP server and CLI can't be wedged by a file.** Input files must be regular files (a FIFO used to block the MCP server for good) of at most 16 MB for MCP tools and 64 MB for the CLI. MCP `plan` never writes into a folder or file whose name starts with "." (such as `.github/`). Run logs are scrubbed of credentials and tokens like printed output before they are written, and unexpected MCP errors are scrubbed too. Shell-quoted commands quote a leading `=`.
- **People confirm what agents plan.** The MCP `apply_command` tool used to return a ready-to-paste command with the confirm hash and the opt-in flags, so a person could run whatever an agent relayed without reviewing it. It now returns only `pricingkit apply <plan>`: the person gets the hash by running `pricingkit diff` themselves, and adds `--allow-base-prices` / `--force-delete` knowingly (the tool says which the plan needs and why). No MCP tool returns a confirm hash any more (`plan` and `diff` leave it out). `pricingkit apply` at a terminal now always prints a summary (app, ops by kind, base-price ops, deletes, existing-subscriber moves) and asks for the app's bundle ID or package name (with `--workspace-plan`, the number of apps) before loading credentials; `--yes` is refused at a terminal and only meant for CI, where runs are unchanged. The docs recommend the `PRICINGKIT_EXPECT_*` pins for MCP servers.
- **Undo never deletes an introductory offer the run didn't create.** On resume, intro territories found in place used to be claimed as created by the run when an attempt had been sent, even if they were an identical offer someone else had made in a territory the run never sent; undo with `--force-delete` then deleted it. The run log now records, before each send, the territories sent (`sentTerritories`), and a resume claims only those.
- **`diff` shows when a plan moves existing App Store subscribers.** A plan op with `preserveCurrentPrice: false` (existing subscribers get the new price) used to look like any other change unless the plan carried planner notes, which aren't covered by the hash. `diff` now computes the existing-subscriber class from every op, marks such ops MOVES EXISTING SUBSCRIBERS and warns at the top (`movesExistingSubscribers` in `--json`). Undoing a decrease that reached existing subscribers no longer raises their price back: the undo op keeps their price (`preserveCurrentPrice: true`) and the undo plan says so.
- **`pricingkit` prints untrusted text as text.** Plan text (warnings, notes, skip details, offer keys, descriptions), store messages and errors could carry terminal escape sequences, so a crafted plan could clear the screen and make `diff` show "No changes" while its hash still matched. Control characters, ANSI/OSC sequences, Unicode direction overrides and zero-width characters are now shown escaped (`\x1B[2J`) on stdout and stderr; `--json` output escapes them inside strings.
- **Confirm hashes are SHA-256.** `apply --confirm` used to take a 64-bit FNV-1a hash, which is not collision-resistant: someone who writes both plans can find a benign and a harmful plan with the same hash. Every plan and workspace plan index is now confirmed with the first 32 hex digits of SHA-256, whatever its `schemaVersion` (a version field is part of the file, so it can't select a weaker hash). Plans are written as schema version 3 and indexes as version 2, so older builds refuse them; files from older builds are still read and hashed the same way. Run logs and the web apply route accept only the 32-digit hash.
- **Google Play bulk updates are previewed and confirmed.** The bulk modal now shows every region's current and new price first, and applies only what it showed: `/api/bulk` takes `dryRun: true` for the preview, and a write must carry the previewed prices (`expectedPrices`); a region whose price changed in between is left alone and reported, and the write itself re-checks the previewed prices against a fresh read just before sending (`PRICE_CHANGED`). Repeated items, or a subscription and one of its base plans, write each base plan once. "Set fixed price" names its currency and changes only regions billed in it (it used to set the same number everywhere, 9.99 becoming ¥10); fixed prices can't be negative; product IDs, base plan IDs and regions are validated.
- **Content-Security-Policy:** `'unsafe-eval'` is gone outside `next dev`, and `base-uri 'none'`, `form-action 'self'` and `object-src 'none'` are added. Checked on the Workers preview, HTML pages included. Inline scripts are still allowed (a nonce-based policy needs a proxy that makes every page dynamic; deferred).
- **Apple read routes check the subscription belongs to your app**, as the write routes already did: the subscription page, price points, batch price points, offers and the price export (which used to label another app's prices with your bundle ID). The price-points routes accept only a numeric subscription ID, and every App Store Connect path segment is URL-encoded, so a crafted ID can't reach another App Store Connect endpoint with your key.
- **The operator's Open Exchange Rates key can't be drained.** Exchange-rate misses on the operator key share one upstream request and a failed one is remembered for 5 minutes (requests with a user's own key run separately, so a bogus key can't make other visitors' requests fail), results are also kept in Cloudflare's shared cache across isolates, and upstream requests time out after 10 seconds. `?refresh=true` now re-fetches only with the user's own key saved in Settings; with only the operator key (`OPEN_EXCHANGE_RATES_APP_ID`) it is served from the cache. World Bank PPP data gets the same sharing and failure cache, and a forced refresh at most every 10 minutes per instance. Upstream error bodies are no longer copied into errors.
- **Cross-site requests are refused.** Every route that changes something now requires a same-origin browser request (`Sec-Fetch-Site`, or a matching `Origin`) and a JSON body. Before, a cross-site HTML form could sign a visitor in to an attacker's account (login CSRF) or plant an Open Exchange Rates key. Requests with neither header (scripts, curl) are still accepted. **Scripts calling the API** must send `Content-Type: application/json`.
- **Sign-in is harder to abuse.** Google sign-in accepts RSA keys of 2048 to 4096 bits only, checked before the key is imported (a 16384-bit key used to cost about 230 ms of CPU per request, billed on Workers); both sign-in routes are rate limited (10 per client per 10 minutes with `TRUSTED_CLIENT_IP_HEADER`, 300 per instance), so they can't be used to check stolen keys at speed; package names and bundle IDs are validated, and an unknown package name is no longer echoed back.
- **Request bodies are capped**: 16 KB for sign-in, app switching and settings, 1 MB for everything else, checked against `Content-Length` and while reading. Saving an Open Exchange Rates key checks the anonymous rate limit before reading the body, and accepts only an app ID's characters.
- **Sessions expire on the server.** The 24-hour limit used to be only the browser cookie's lifetime: a copied session cookie kept working until `ENCRYPTION_KEY` changed (in a test, 400 days later), and old-format cookies were re-issued with a fresh lifetime. A session cookie is now an encrypted envelope (`{ v, typ, iat, exp, creds }`) whose absolute expiry the server checks on every request and never extends; its encryption is bound to the cookie's name and the session version, so an App Store session can't be presented as a Google one; and its contents are checked after decryption. `SESSION_VERSION` signs everyone out. Legacy cookies are accepted until 2026-11-10, after a size and format check that refuses junk before any key derivation (each legacy read cost a 100,000-iteration PBKDF2 run, which anyone could trigger with a made-up cookie).
- **`ENCRYPTION_KEY` must be base64 of at least 32 bytes with at least 16 distinct byte values** outside `next dev` (a format check: it refuses passphrases, short keys and repeats like `AAAA...`, but can't prove a key random), and its bytes (not its text) are the key-derivation input. HKDF doesn't stretch keys, so a weak key could be guessed offline from a session cookie.
- **Cookies use the `__Host-` prefix** in production, so a sibling subdomain can't set or shadow them. During the legacy window only old-format cookies are read under the old names; a current-format session planted under an old name is refused.
- **Google sessions keep only `client_email`, `private_key_id`, `private_key` and `project_id`.** Extra fields in the uploaded JSON could push the cookie past the browser's 4 KB limit, and the browser dropped it while sign-in reported success; credentials too large for a cookie are now refused at sign-in.
- **Signing out clears everything:** both store sessions, the saved Open Exchange Rates key (a year-long cookie) and the tab's "verified" flag; a sign-out the server didn't confirm is reported instead of looking done.
- **Don't run `npx pricingkit` outside a clone.** The README used to suggest it, MCP configuration included. PricingKit is not published to npm, so outside the clone `npx` would download whatever the registry holds under that name and run it with your store credentials. The docs now run the launcher by path (`node /path/to/pricingkit/bin/pricingkit.mjs`, or `command: node` with that path in an MCP client) or `npm exec --prefix <clone> --no-install pricingkit`; any remaining `npx` carries `--no-install`. If you configured an MCP client with `npx pricingkit mcp`, change it.
- The CLI launcher turns off tsx's disk cache (`TSX_DISABLE_CACHE=1`, set before tsx loads). The cache is a shared temporary folder whose compiled files tsx trusts, so on a multi-user machine or shared CI runner another user could have planted code there.
- Dependencies: Next.js 16.4.3 and `@opennextjs/cloudflare` 1.20.13 (the versions running in the Worker), `zod` 4.6.7 and `yaml` 2.9.1 (no longer pinned to the vulnerable 2.8.2); `wrangler` 4.153 for deploys (it ships a pre-release `miniflare` 5 for local preview); `@types/node` follows Node 22. The new `eslint-config-next` reports two React Compiler rules (`react-hooks/set-state-in-effect`, `react-hooks/immutability`) that existing components break; they are warnings for now.
- Session cookies are encrypted with a key derived once from `ENCRYPTION_KEY` with HKDF-SHA-256 instead of 100,000 PBKDF2 iterations per request. Existing cookies are still read and re-encrypted on their next request (until 2026-11-10, see above), so nobody is signed out. `ENCRYPTION_KEY` must be 32 random bytes in base64 (`openssl rand -base64 32`), since HKDF doesn't stretch weak keys.
- CLI output files (plans, state snapshots, run logs) are always written to a new temporary file and renamed into place; a target that is a symbolic link, not a plain file, or has more than one hard link is refused. The MCP server refuses a `plan` call sent as a notification (no id), decodes UTF-8 split across reads, and `apply_command` says how many ops a resume log already records as done.

- Apple JWTs and Google access tokens are cached per full credential (SHA-256 of the key, 50-entry LRU). On a shared instance, two users whose keys share a Key ID or client email can no longer receive each other's token.
- Reading a session cookie without `ENCRYPTION_KEY` no longer falls back to plaintext base64 outside `next dev`; the cookie is ignored and the request is treated as signed out. Previously any build without the key, production included, would accept a plaintext base64 cookie.
- Public endpoints return generic error messages; upstream error details are logged server-side only.
